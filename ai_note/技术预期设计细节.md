# 技术预期设计细节

记录日期：2026-11-15。本文记录评审式讨论中明确的实现构想、理由及待验证问题，为申报书第五节提供技术设计依据。构想不等于已实现或已验证；架构职责仍由《架构设计.md》维护。

## 一、技能能力的发现与使用

### 已明确的构想

不同具身模型、传统算法和服务具有不同的功能边界、输入要求与调用方式。Agent 需要相应的 skill 使用说明，了解能力用途、适用条件和使用方法，再调用实际执行能力。

此处 skill 指指导 Agent 使用能力的说明，与执行层的“技能专家”区别记录。说明的具体载体、字段与加载机制尚待确定。

拟将网络请求封装为异步 CLI 工具，Agent 通过 CLI 使用远端能力，减少逐项开发复杂 Agent 工具插件的工作。该路径是目前认为方便的候选实现，仍需验证引擎运行环境、参数传递、异步结果及事件回流。

技能专家通过网络服务暴露接口，人工操作前端可调用相应接口，在不依赖 Agent 的情况下验证专家本身是否可用，并辅助诊断执行问题。

拟议调用关系：

Agent 获取能力使用说明 → 调用 CLI → CLI 向技能服务提交请求 → 服务调用实际专家。

异步任务由常驻 env 主程序持续跟踪。env 主程序拟嵌入 pi Agent SDK，承载引擎与会话运行，维护任务上下文，接收技能进展、结果和其他外部事件，并据此调度 Agent 后续决策。CLI 是任务提交或查询入口，不承担主程序保活职责；Agent 无需持续轮询来维持任务运行。具体事件传输及订阅方式仍待确定。

### 服务实现的候选

技能转接服务可先使用 FastAPI 等后端框架接收请求并运行专家，以 HTTP 降低通信实现复杂度、尽快验证能力；也可根据交互需求采用 WebSocket 双向通信，必要时再优化。上述均是候选，不是已冻结协议。

转接、通信与状态管理应写入所在层的实现；胶水机制贯穿各层，不单独增加功能层。

### 待讨论与验证

- 能力使用说明的组织、加载与更新方式。
- 异步 CLI 提交后如何返回受理结果及任务标识，如何处理提交失败或受理结果丢失。
- 主服务、CLI 和技能服务之间的任务标识与事件关联。
- 人工面板与 Agent 使用同一接口时的控制权、状态和资源占用。
- 长驻模型、设备控制与请求服务的进程关系。

## 二、env 主程序与事件驱动运行

沿用既有设计：pi Agent SDK 嵌入常驻 env 主程序，由 env 主程序保活并承载引擎运行。Agent 经 skill 说明使用 CLI 提交能力请求；任务实际执行独立于 CLI 进程及单次模型调用。执行事件回到 env 主程序，主程序关联任务、维护状态，再在适当时机更新会话并调度 Agent。事件驱动是既定设计，不重新将 Agent 轮询列为对等候选；查询可用于状态核对和恢复。

## 三、宿主语言与通信场景（待讨论方案）

本地 pi 的 `packages/coding-agent/docs/rpc.md` 与包定义确认：进程内 SDK 集成面向 Node.js/Bun；其他语言可经标准输入输出 JSONL RPC 控制常驻 pi 子进程。因此，按用户最新构想，优先考虑 Node.js 主程序承载 pi SDK；Python 可实现模型、感知和技能服务。Python 直接进程内加载该 SDK 不是当前路线。

以下是供讨论的场景化建议，尚未定案：

- 同机或局域网技能：CLI 经 HTTP/JSON 提交请求，服务返回受理结果与任务标识；实际专家独立执行，env 统一接收状态事件。
- 主动订阅事件：env 向技能服务建立 SSE 连接接收进展及结果，另用 HTTP 查询和取消。适用于请求与通知分工清楚、env 能访问服务的部署；连接重建需要状态核对，SSE 本身不保证业务事件不丢失。
- 服务主动通知：技能服务经 HTTP 回调 env 的事件端点，适用于双方地址可达且配置回调方便的部署；仍需任务关联、重复处理及失败补查。
- 持续双向通信：WebSocket 同时传递命令与事件，适用于交互密集或有双向会话需求的部署；需自行定义请求关联、重连和未决任务恢复，不能仅凭双向连接认定比 HTTP/SSE 更可靠。
- 人工面板：复用同一技能服务的调用接口，不必经过 Agent；是否经 env 统一管理任务与资源待确认。
- ROS 2/DDS：可保留用于支撑层的传感器、状态和 action，env 经适配服务访问；没有必要仅因底层使用 ROS 2，就让 Node.js 主程序直接处理全部 DDS 通信。具体是否桥接以任务接口及部署需求判断。

通信选型先依据服务部署位置、连通条件、事件方向及人工调试需求确定，不要求各层统一协议。以上设计需在场景讨论后收敛，暂不直接写为第五节既定选型。

## 五、事件接入与分布式专家的职责确认

- Node.js env 承载 pi SDK，复用 SDK 原生的消息、工具执行及运行生命周期事件；env 负责将外部机器人业务事件与任务状态、Agent 会话衔接，不重复实现引擎已有的事件机制。
- SSE 与 WebSocket 均为候选，以原型中的实现复杂度、运行稳定性及恢复表现决定，哪种简单稳定就采用哪种，目前不冻结协议。
- 技能专家后端负责处理实际专家可能分布在不同主机的问题，包括向相应执行服务转接请求及回传执行状态；env 和 CLI 面向后端提供的能力接口，不承担逐个专家的主机寻址与分布式调用细节。
- 主机分布不直接决定 env 事件通道采用 SSE 还是 WebSocket，两者按各自职责分别设计。

## 六、首个技能专家与能力边界的形成

### 用户明确的设计与技术倾向

总体设计按各技能专家自身的能力边界确定封装，不预先要求不同专家具有相同的任务范围。

SmolVLA 是目前高度倾向采用的首个技能专家，首期技能应用聚焦物品抓取；具体物品集合和可执行范围由实际训练、调优与测试结果决定。例如，若模型训练于小木块且对其他目标表现不佳，能力说明就应限定为经验证的小木块抓取，不因采用具身模型而宣称可抓取任意物品。此处“物品抓取”说明首个专家的应用重点，不据此替换既定整机寻物取回主场景。

多任务训练等调优可能扩大或改变能力范围，但也可能出现灾难性遗忘。需要在新任务表现与原有任务保持之间评价训练效果，据实更新专家的能力边界；尚不认定某种训练方法已经解决遗忘问题。

因此，专家能力规范不是仅在接口设计时一次写定：模型应用、数据采集、训练调优与测试共同决定其可声明的任务、物品及条件范围。能力变更后应同步维护使用说明及对应模型版本，具体维护机制仍待设计。

### 对第五节的约束

技术路线应明确 SmolVLA 作为首个专家的优先方向，展开其本体适配、训练调优、抓取应用与边界验证，不以泛泛罗列候选模型替代。总体架构仍保留其他技术的接入空间；后续专家按各自能力边界设计。

## 七、已有 SmolVLA 概念验证与后续讨论方式

记录日期：2026-11-16。以下为用户报告的已有实验，尚未核对代码、数据及测试记录：

- 六轴机械臂，仅使用腕上摄像头。
- 使用50条抓取数据进行验证，用户评价数据质量偏差，成功率约20%，仍有优化空间；测试次数、成功判据及分布尚未记录，不将该数字作为正式对照结果。
- 执行连接为 LeRobot 自定义 robot 类，经 TCP 与 ROS 2 侧通信，ROS 2 节点再经串口连接机械臂 MCU 固件。
- 摄像头不经 ROS 2 接入。其具体采集与同步方式尚未展开。

这一结果提供模型—LeRobot—ROS 2—MCU—机械臂链路的可运行经验，不代表移动操作、技能服务化或整机闭环已经验证。后续技术设计需考虑复用该链，而非默认重建模型控制接口。

讨论方式按用户纠正调整：先覆盖机器人各部分的基本设计及协作关系，建立完整数据流与控制流，再根据跨层依赖深入关键问题；不在单个模型或技能方向持续深挖而遗漏整体设计。

## 八、搜索策略与 Agent 判断的职责

记录日期：2026-11-16。用户明确：在可用能力及其使用说明范围内，如何组织搜索应由大语言模型驱动的 Agent 判断，不在总体设计中预设唯一的导航—搜索分解方式。

例如，Agent 可以查询候选位置，导航到高概率位置附近，再调用相机角度调整、观测或预设搜索程序；若存在适用的复合搜索技能，也可以直接调用。具体做法取决于当时可用的技能、环境信息和执行结果。相机可控程度与具体搜索服务尚未确定，上述为可能的能力组合，不表示均已实现。

Agent 的能力选择、组合与反馈判断是 Agent 层的重要职责。设计应提供清楚的 skill 说明、可调用接口、环境信息与执行反馈，而不是把所有任务流程预先替 Agent 编写。底层仍负责技能内部执行、资源约束及设备保护。

GPT-6.1sol 等模型是用户举出的判断能力来源示例，其在本项目工具集和真实反馈条件下的表现需通过实验评价，不视为已有机器人任务效果证据。

## 九、感知配置与平台演进

记录日期：2026-11-16。用户说明已有2D雷达，后续还会有一个固定在机器人身上的雷达；后者类型及与已有雷达的关系尚未展开，保留原述，不自行改写为相机或认定为3D雷达。此前已确认机械臂概念验证使用腕上摄像头。

机器人形态仍处于初期，硬件可能升级。3D雷达、深度相机及多摄像头均为扩展方向，具体配置根据后续任务、模型应用和系统工作确定，不作为当前已具备或首期必需条件。

技术路线应依据实际传感器提供的信息设计感知与空间定位接口，明确依赖深度输入的候选方案所需条件，不能默认RGB-D已经可用。平台升级后需重新处理坐标、标定、数据接入及相应技能适配，保留上层接口复用的设计目标。

## 十、持续观测与 Agent 使用环境信息

记录日期：2026-11-16。用户明确：优先持续观测环境，算力受限时再调整这一安排。Agent 通常读取环境认知服务提供的数据，环境观测与状态维护不以每次 Agent 调用为前提。

据此，感知处理和环境更新应能独立于模型决策持续运行；具体处理频率、采样与算力分配待配置及实测确定，不将“持续观测”解释为所有模型必须逐帧全速推理。主动搜索、调整视角等任务能力仍可由 Agent 按需调用，与后台观测互补。

## 十一、移动与操作的阶段衔接

记录日期：2026-11-16。用户明确：前期采用底盘停车后再操作的方式，降低移动操作耦合难度。后续若采用协同控制，可在导航结束后将底盘控制权移交给协同控制模块；SLAM 定位保持运行。控制权移交与定位服务的生命周期需要区分，不将导航结束理解为停止定位。

停车状态如何确认、操作所需的相对位置如何获得，以及控制权移交的具体接口尚未展开。

## 十二、搜索动作与持续环境认知的分工

用户明确：搜索技能、Agent 调用姿态调整能力或其他搜索方式，均可通过改变机器人及传感器姿态获得新的观测条件。对环境和物体的感知持续由环境认知服务提供，Agent 及相关技能依据该服务的数据判断搜索效果，不将每一种搜索方式都设计为独立的物体识别与地图维护系统。

搜索的动作组织保留灵活性，不预设唯一流程；具体硬件配置与搜索实现根据后续工作确定。技术路线应说明支撑这些能力的技术及接口关系，区分当前优先实现与可演进的选择，不把架构允许的多种实现写成首期全部实现的承诺。

## 十三、空间感知与概率推断的拟研究路线

用户提出 RTAB-Map 作为视觉建图候选，具体输入配置及尺度条件需结合实际设备核对。需要三维感知时，可增配深度相机或三维雷达开展三维建图；早期可将物体放在地面上，降低场景难度。开放词汇检测或分割结果结合相机标定、位姿 TF 及地面约束或深度信息，可转换为地图中的物体位置；开放词汇分割与三维点云关联可参考已有对象级建图方法。环境语义地图精度按任务需要确定，不以高精度重建为默认目标。

实例关联与位置推断保留两类研究路线：基于神经网络等技术的较重型跟踪方法，以及概率估计与经典多目标跟踪算法。具体方法的比较、组合及取舍属于研究工作，不要求立项时冻结最终算法。

## 十四、分布部署与可行性论证的尺度

轻量模型可本地部署，计算需求较大时可使用推理服务器。网络服务与 ROS 2/DDS 等通信机制为分布部署提供条件，具体设备与计算分配按后续模型选择和实测确定。

技术路线是拟开展的技术探索：需说明已有依据、候选实现、关键依赖及研究取舍，不以全部算法、协议、硬件和部署细节预先确定作为可行性的前提。后续论证区分已有概念验证、已有技术可支撑的实现路径，以及仍需实验检验的研究效果。
