# Agent 层与胶水层设计讨论总结

## 1. 项目背景

项目目标是家居移动操作机器人，典型任务包括：

- 根据用户指令寻找并取回物品；
- 自动发现垃圾、拖鞋乱放等问题并进行整理；
- 后续扩展到更复杂的家务任务。

总体架构初步分为：

```text
Agent 大脑层
原子任务 / 技能专家层
语义地图层
支持层
硬件层
```

当前会话重点不是冻结完整项目设计，而是研究 Agent 层、技能专家接入方式和多机分布式胶水层的可行方案。

## 2. 核心认识

VLA、WAM、ACT、LeRobot 具身模型以及传统运动学算法，各自只适合一定范围的短程任务，不适合作为任意复杂任务的统一解决方案。因此可以把它们封装为不同的“技能专家”，由 Agent 根据任务目标、环境状态和技能能力进行选择与编排。

Agent 层主要负责：

- 理解用户意图；
- 分解长程任务；
- 选择和调用技能；
- 维护会话、任务上下文和记忆；
- 根据技能结果和环境变化继续规划；
- 在失败、不确定或需要确认时进行恢复或询问。

Agent 不应直接控制电机，也不应直接依赖某个 VLA、ACT 或运动规划器的私有 API。底层执行应经过统一的技能接口、安全检查和任务运行时。

## 3. pi agent 与 LangChain 的初步判断

当前第一候选倾向于 pi agent，原因是：

- Pi 的 `AgentSession` 将会话作为一等对象；
- SDK 可以嵌入 Node.js 或 Bun 进程；
- 支持 `prompt()`、事件订阅、会话持久化、工具和扩展；
- 支持 `abort()`、`waitForIdle()` 以及流式事件；
- 可以自定义模型运行时、会话管理器、资源加载器和工具集合；
- 轻量、可控，适合由项目自己掌握外层任务运行时。

官方 SDK 文档确认的关键能力包括：

- `createAgentSession()` 创建 Agent 会话；
- `session.prompt()` 发起任务；
- `session.subscribe()` 监听消息、工具执行、队列、重试和运行生命周期事件；
- `session.abort()` 中止当前操作；
- `session.waitForIdle()` 等待会话空闲；
- `agent_end` 表示一次底层 Agent 运行结束，`agent_settled` 更适合判断 Pi 是否不会继续自动执行；
- SDK 可使用持久化或内存中的 `SessionManager`；
- 可通过 `customTools`、扩展和资源加载器接入项目能力。

LangChain/LangGraph 仍有价值，但更适合作为对照方案：

- LangChain 更偏模型、工具、检索和集成生态；
- LangGraph 更偏显式状态图、检查点、暂停、恢复和人工介入；
- 如果项目后续需要复杂的持久化工作流和状态恢复，再评估是否引入 LangGraph；
- 当前不应因为生态规模而过早引入更重的抽象。

OpenCode 可以作为 Agent harness 和交互式 Agent 产品形态的参考，但目前没有充分理由把它作为机器人 Agent 层的主要运行底座。

## 4. 建议的 Agent 层结构

```text
常驻事件驱动任务运行时
        |
Pi Agent Session
        |
技能注册表 / Tool Adapter
        |
任务编排与安全执行层
        |
外部技能服务、语义地图服务、机器人状态服务
```

行为树、任务调度器或常驻主程序负责：

- 常驻运行；
- 任务优先级；
- 超时、取消和恢复；
- 周期性活动；
- 安全状态和确定性流程。

Pi 适合在这些位置被调用：

- 需要理解复杂目标并分解任务；
- 需要在多个技能中进行选择；
- 技能失败后需要重新规划；
- 环境发生重大变化；
- 需要向用户询问或请求确认。

导航、抓取、姿态控制、急停和底层安全约束不应依赖大模型自由生成。

## 5. 技能专家与 ROS2 的关系

原子任务执行层不应被默认视为 ROS2 的一部分。VLA、WAM、ACT、LeRobot 模型服务和传统运动学算法可以作为独立进程或独立服务器，通过 TCP、gRPC、WebSocket、HTTP 或专用协议接入。

更准确的关系是：

```text
硬件和机器人基础能力
        |
ROS2 / 厂商 SDK / 控制接口
        |
原子任务执行服务
  VLA / ACT / WAM / 传统算法
        |
网络协议
        |
Agent 层或胶水层
```

Agent 看到的应是稳定的能力接口，例如：

- `find_object`
- `inspect_scene`
- `navigate_to`
- `grasp_object`
- `place_object`
- `ask_user`

而不是直接看到 `run_ACT_model`、`call_MoveIt` 等实现名称。

## 6. 胶水层的网络化方向

由于语义地图、LeRobot 具身模型、ROS2 生态算法和远程推理服务可能部署在不同进程或不同机器上，胶水层采用网络通信是合理的。网络是通信基础，FastAPI 等后端框架只是服务端实现方式，两者不是互斥选择。

初版建议：

```text
HTTP/JSON：任务提交、状态查询、地图查询、取消、管理
SSE/WebSocket：任务进度和事件推送
gRPC/TCP：需要严格类型、双向流或更高性能的服务间调用
ROS2：机器人内部传感器、控制和确定性执行接口
UDP：只用于明确的实时数据场景，不作为一般任务请求协议
```

第一版可采用 FastAPI 构建控制面服务：

```text
POST /tasks
GET  /tasks/{task_id}
POST /tasks/{task_id}/cancel
GET  /map/objects
GET  /events
```

任务应采用异步提交：提交后立即返回 `task_id`，后续查询状态或订阅事件，不让一次 HTTP 请求阻塞到远程推理、导航或抓取结束。

## 7. CLI 胶水层想法

将网络 API 封装为 CLI 是可行的，并且具有很强的工程价值：

- Agent 可以调用结构化 CLI 工具；
- 人工可以直接调用同一套接口；
- 可以用脚本测试各层行为；
- Agent 层可以被剥离，先独立验证地图、技能和机器人服务；
- CLI 进程退出不会影响常驻任务状态。

建议将 CLI 定位为无状态控制面客户端，而不是整个异步运行时：

```text
robot task submit ...
robot task status <task_id>
robot task wait <task_id>
robot task cancel <task_id>
robot robot state
robot map query ...
robot events
```

真正的任务队列、状态存储、事件处理和技能调度由常驻 orchestrator 负责。

Pi 可以通过 custom tool 调用 CLI，也可以调用同一套共享客户端库：

```text
Pi custom tool -> robot-cli -> 胶水层 API
人工终端      -> robot-cli -> 胶水层 API
```

## 8. 异步会话续接

建议把消息分成三类：

- 用户消息：改变目标或提出新要求；
- 环境事件：地图、物体和机器人状态变化；
- 任务结果：技能完成、失败或需要恢复。

不要把三类内容都伪装成普通用户文本。外层运行时应保留事件类型、来源和关联任务 ID，再决定如何注入 Pi 会话。

典型流程：

```text
用户提出目标
  -> Pi prompt()
  -> Agent 调用 submit_task
  -> 胶水层返回 task_id
  -> 编排层异步执行
  -> 编排层发布 task_completed / task_failed
  -> 外层调用 session.followUp() 或等价会话接口
  -> Pi 继续推理、回答或调用下一技能
```

Agent 不应依赖高频轮询作为主要机制；正常路径应由任务完成事件触发会话继续，轮询作为降级和人工调试方式。

## 9. 需要优先验证的最小原型

不需要真实机器人即可验证整体设计。可以先实现三个模拟技能：

- `find_object`
- `navigate_to`
- `grasp_object`

验证以下流程：

1. 用户输入“找到水杯并拿给我”；
2. Pi 选择并调用技能；
3. 胶水层异步返回任务 ID；
4. 模拟技能发布进度和完成事件；
5. 外层把完成结果注入同一 Pi 会话；
6. Pi 继续执行下一步或向用户回复；
7. 测试失败、取消、超时和人工 CLI 调用。

## 10. 尚未确定的问题

- Pi SDK 中 custom tool 与外部异步任务的最佳封装方式；
- 任务完成后应使用哪种会话续接机制；
- CLI 与 Agent 是使用子进程调用还是共享客户端库；
- HTTP/SSE、WebSocket、gRPC 和自定义 TCP 的具体边界；
- 事件总线是否需要独立消息代理；
- 语义地图服务的查询和更新协议；
- 远程推理服务的鉴权、超时、取消和断线恢复；
- 技能能力描述、前置条件、资源占用和失败原因的统一格式；
- 是否需要 LangGraph 负责显式任务状态图和持久化恢复。

## 11. 当前阶段结论

目前最合理的探索路线是：

1. 以 pi agent SDK 作为第一候选 Agent 推理引擎；
2. 自己掌握常驻事件驱动任务运行时；
3. 用统一技能接口屏蔽 VLA、ACT、WAM、LeRobot 和传统算法差异；
4. 用 FastAPI/HTTP 构建第一版胶水层控制面；
5. 用 SSE 或 WebSocket 处理事件和进度；
6. 用 CLI 同时服务 Agent 调用、人工调试和自动化测试；
7. 先用模拟技能完成异步会话闭环，再接入真实地图、远程模型和 ROS2 适配器；
8. 根据实际复杂度决定是否引入 LangGraph 或消息代理。

当前不应过早冻结具体网络协议或完整分布式架构。优先验证任务语义、事件生命周期、会话续接和人工可调试性。
