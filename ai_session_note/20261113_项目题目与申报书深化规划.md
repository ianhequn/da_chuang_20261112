# 2026-11-13：项目题目与申报书深化规划讨论

## 一、会话目标

本会话继续推进大创申报书编写。当前阶段暂不直接展开申报书正文，而是先明确项目对象、题目表达、研究边界和后续规划基础。

## 二、项目题目调整

原题目：

> 融合语义地图的 Agent 驱动具身移动操作机器人可扩展通用架构研究

讨论认为，原题目过于突出“架构研究”，容易让评审将项目理解为面向开发者的软件架构设计，不容易形成对机器人对象、任务形态和最终成果的直观印象。

经过讨论，暂定第二版项目名称为：

> **Agent 驱动的可扩展具身移动操作机器人**

不在题目中加入“研究”。题目暂时不限定家庭、取物、整理等具体场景，也不限定某一种具身模型，保留后续扩展不同任务和技能实现的空间。

## 三、题目中各概念的含义

### 1. Agent 驱动

Agent 负责理解用户目标、拆解长程任务、选择和调用技能、根据执行结果调整计划，并处理完成、失败、超时和环境变化等事件。

Agent 不直接承担电机级控制、实时闭环或安全保护。

### 2. 可扩展

“可扩展”需要在正文中具体化，不能只作为宣传性表述。主要包括：

- 增加新的技能服务；
- 替换技能内部的模型、算法或实现；
- 适配不同机器人硬件和软件环境；
- 从一个验证任务扩展到多个相关任务；
- 在不重写 Agent 核心逻辑的情况下重新组合能力。

### 3. 具身移动操作机器人

研究对象是一类同时具备移动、感知和操作能力的机器人系统，而不是单一机械臂、单一移动底盘或单个具身模型。

### 4. 语义地图

语义地图仍然是项目的重要技术支撑，但不一定放入最终标题。它负责管理空间、区域、物体、历史观测和候选位置，为 Agent 的任务决策提供环境状态信息。

## 四、关于“技能服务”的讨论

可以从 Agent 的调用接口角度，将导航、视觉搜索、抓取、放置、语义地图查询与更新等能力统一封装为“技能服务”。这样 Agent 不需要依赖具体模型或算法，只需要使用稳定的服务接口。

但从系统职责上看，语义地图不应简单等同于抓取或导航这类执行技能。更准确的表达是：

> 语义地图作为可调用的环境认知服务，与导航、感知、抓取、放置等执行技能共同构成技能服务体系。

项目中的具身能力也不应限定为具身模型。技能服务可以由 VLA、WAM 等具身模型，也可以由视觉模型、传统运动规划、强化学习策略或其他机器人软件实现。

## 五、当前项目定义

项目可以暂时定义为：

> 研究一类由 Agent 负责任务理解与长程编排，能够调用环境认知、导航、感知、抓取、放置等可扩展技能服务，并在移动和操作过程中完成任务协同的具身机器人系统。

项目要解决的核心问题不是重新训练某个底层模型，而是解决已有异构能力之间的组织、调用、状态管理和协同问题。

## 六、为什么还不能直接开始写申报书

当前题目已经基本确定，但项目目标文档仍然过于简略，还没有充分明确：

- 具体研究对象；
- 核心问题及其实际表现；
- Agent、语义地图和技能服务之间的职责关系；
- “可扩展”的可验证定义；
- 第一阶段验证范围；
- 预期系统、方法、接口和实验成果。

因此，下一步应先深化 `项目目标.md`，形成项目定义和申报书总纲，再从中提炼研究目的、研究内容、创新点和技术路线。

## 七、下一步工作规划

建议将 `项目目标.md` 第二版扩展为以下结构：

1. 项目名称
2. 项目对象
3. 项目要解决的实际问题
4. 总体目标
5. 核心研究问题
6. 系统组成
7. Agent、环境认知服务和技能服务的职责
8. 可扩展性的具体定义
9. 第一阶段验证任务
10. 项目边界
11. 预期成果
12. 与申报书各部分的对应关系

其中第一阶段需要设置一个具体但不限制最终应用范围的验证闭环，例如室内环境中的目标物体寻找、移动接近、识别、抓取、放置和返回。这个任务只是验证载体，不应被写成项目最终唯一应用场景。

## 八、申报书映射关系

- 项目目标 → 研究目的
- 核心研究问题 → 研究内容与拟解决的问题
- 系统组成与职责 → 技术路线
- 可扩展性和技能服务协同 → 创新点与项目特色
- 第一阶段验证任务 → 预期成果与进度安排
- 已有机器人、ROS 2、导航和具身模型基础 → 已有基础
