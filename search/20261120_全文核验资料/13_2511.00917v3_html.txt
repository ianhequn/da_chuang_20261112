 Abstract 
 Today’s dominant route to generalist robots scales robotics data to train end-to-end policies.
We instead use a vision-language model (VLM) as a coding agent that writes robot programs using a curated library of perception, planning, and control tools.
 maestro ’s orchestration harness packages multi-step perception and action procedures into callable tools and guides their use through a plan–act–replan loop, using visual and execution feedback to verify outcomes and recover from failures.
With this tool library and harness, maestro matches or surpasses state-of-the-art vision-language-action (VLA) models zero-shot in our tabletop comparison and performs diverse mobile manipulation tasks, without collecting new teleoperation data or invoking a VLA tool. Ablations show that expanding the tool library improves average task progress with the full harness, while adding tools without it does not reliably improve progress.
 Case studies illustrate maestro ’s potential for autonomous code improvement across trials, faster execution with VLA tools, and automatic robot data generation. We show that expanding robotics tool libraries together with their orchestration harnesses offers a complementary route to general-purpose robots alongside scaling end-to-end robot training data.
 Project site: maestro-robot.github.io . Code: github.com/penn-pal-lab/maestro . 
 Keywords: VLM agents, robotic manipulation, zero-shot generalization 
 1 Introduction 
 The prevailing view in robotics holds that general-purpose capabilities require training a single end-to-end model on massive robotics-specific datasets gathered through teleoperation  [ 1 , 2 , 3 , 4 ] . The scarcity of such data, relative to the text and images available to language and vision models, is widely cited as why robotic systems lag behind, motivating large efforts to scale data collection for vision-language-action (VLA) models. 
 Figure 1: maestro receives language instruction and leverages a set of tools to complete diverse tasks in a zero-shot setting. 
 We take the view that robotics data to inform a generalist robot need not begin and end with such “ observations-in, actions-out ” data.
 In particular, much useful robotics knowledge is readily available through a diverse collection of tools to perform robotics-relevant functions such as object pose estimation, SLAM, semantic object category recognition, or path planning. Each such module represents the cumulative engineering effort of the robotics research community, often over several decades, and informed by various data islands specific to their respective functions. 
 We introduce maestro , a framework for tabletop and mobile manipulation that assembles these islands into one working generalist robotics system. A vision-language model (VLM) acts as a coding agent, orchestrating a curated tool library through a closed-loop harness that monitors and recomposes tools. By replacing the task-specific bespoke human labor of coding and orchestrating specific sequences of functions with dynamically generated code on a VLM, this agentic approach scales modular “old-fashioned”  [ 5 ] approaches to the generalist robotics setting. 
 Without collecting new teleoperation data, maestro matches or surpasses the evaluated VLA baselines in our zero-shot tabletop comparison and performs diverse mobile manipulation tasks. Our evaluation spans pick-and-place, deformable- and articulated-object manipulation, spatial reasoning, tool use, object-affordance reasoning, semantic and memory challenges, long-horizon manipulation and loco-manipulation, and active exploration. In our ablations, the full toolset and harness achieve 76.9% average task progress. Removing the harness reduces this to 33.0% (43.9 percentage points lower); retaining the full harness but removing the added robotics tools reduces it to 32.3% (44.6 points lower; Fig.  7 ). 
 maestro also inherits the advantages of manually engineered modular systems: interpretability, debuggability, and extensibility. New tools, including VLAs, integrate with minimal effort, and adapting to new embodiments or improving from limited experience requires only localized code edits, not retraining or large-scale data collection. 
 These advantages currently come at higher latency and computational cost than end-to-end VLA policies, a limitation that will ease as the VLM inference stack improves.
We also show another solution route: maestro can generate robot data automatically (App.  L ), which could support distillation into lightweight imitation policies  [ 5 ] . Large VLMs, including GPT-6 Astra  [ 6 , 7 ] , are now being used to generate robot actions directly. They offer broad reasoning capabilities but have high inference latency and token usage. Smaller VLA policies provide faster control but can struggle with open-ended, reasoning-intensive tasks.
 maestro explores an intermediate approach: retain VLM reasoning for planning and program synthesis, while using existing or pretrained skills for perception and control. 
 In summary, our contributions are: 
 1. 
 We introduce maestro , a framework that makes a VLM coding agent into a generalist robot policy by combining a curated robotics tool library with an orchestration harness for composing tools, verifying outcomes, and recovering from execution failures. 
 2. 
 We show that maestro matches or surpasses the evaluated VLA baselines and our code-as-policies baseline zero-shot in our tabletop comparison, without new teleoperation data or VLA tool use. We also demonstrate maestro ’s capabilities in long-horizon mobile manipulation. 
 3. 
 Our systematic ablations show that expanding the tool library improves average task progress with the full harness, while adding tools without it does not reliably improve progress (Fig.  7 ). 
 4. 
 Our case studies demonstrate maestro ’s potential to autonomously improve its code across trials, execute tasks faster with VLA tools, and generate robot data. 
 Rollout videos for all real-world experiments and an interactive agent dashboard (perception, code, and rollout views) are on our project site . 
 2 Related Work 
 Modern vision-language-action (VLA) foundation models for robotics typically start from pre-trained VLM/LLM backbones and fine-tune on large quantities of robotics-specific data  [ 8 , 9 , 10 , 11 , 2 , 12 , 13 , 14 , 4 ] , including hierarchical and reasoning-augmented variants  [ 10 , 9 ] ; in all of these, action selection still flows through a fine-tuned VLA. We are instead interested in directly using off-the-shelf VLMs and LLMs in the robotic control loop.
Among such applications of “VLMs and LLMs as policies”, one approach generates low-level robotic actions directly  [ 15 , 6 , 7 ] , while another generates “code as policies”.
CaP  [ 16 ] first demonstrated a text-based LLM orchestrating a small set of perception and control APIs into a program, but the generated program is static and open-loop  [ 16 , 17 , 18 ] . More recent work closes the loop with VLMs, generating and revising code from visual feedback within a trial  [ 19 , 20 , 10 ] . 
 maestro studies how a VLM-based harness can orchestrate a broad robotics toolset across manipulation tasks, with ablations evaluating the roles of the toolset and harness. This modular approach is similar to the good old-fashioned engineering (GOFE) discussion  [ 5 ] , which emphasizes combining model-based robotics with learned components. 
 Direct VLM-based robot control remains challenging, particularly for precise and dexterous manipulation. Many leading VLA systems achieve broad manipulation capabilities but rely on substantial, costly real-world teleoperation  [ 1 , 12 , 2 , 3 , 14 , 4 ] ; complementary data sources include simulation  [ 21 , 22 , 23 ] and human videos  [ 24 , 25 , 26 ] . The original zero-shot code-generation setup in Gemini Robotics  [ 2 , 4 ] illustrates these challenges: its reported zero-shot dress-folding trials were unsuccessful, with insufficiently precise grasp generation identified as the main difficulty. We adopt the Gemini Robotics agent as our Base CaP reference system and the state-of-the-art π 0.5 \pi_{0.5} model  [ 12 ] as a strong VLA baseline; Sec.  3.1 describes how Base CaP works and how maestro departs from it by composing external robotics models as callable tools rather than relying on the VLM for perception. We show that scaling the right set of tools and harnesses for a coding agent is a complementary axis to scaling robot data, and maestro can further call VLAs as tools where they excel. App.  F extends this discussion to VLMs and LLMs as modular components and to concurrent code-as-policies efforts. 
 Concurrent code-as-policies efforts include CaP-X  [ 27 ] , which benchmarks and improves embodied coding agents, and GaP  [ 28 ] , which builds graph policies from modular robot skills. maestro focuses on a broad robotics toolset and its orchestration harness for real-world generalist manipulation, with ablations that examine their respective roles. 
 3 Method 
 We call our approach M anagerial A gent for E xecuting S ensorimotor T asks in RO botics, or maestro for short.
 maestro is a robotic system centered on an agent that writes and executes code to leverage a toolkit spanning perception, geometry, control, pre-trained policies, and image editing. 
 To specify a task,
 maestro receives a system prompt, a scene image, and task instructions.
This design forms an adaptive perception–action–learning loop; we begin from the Base-CaP starting point (Sec.  3.1 ) and build up from there. An overview of this loop and the API is shown in Fig.  2 , with the per-trial execution loop formalized in Algorithm  1 and the full execution-and-evolution loop in Algorithm  2 (both in App.  A ).

 3.1 Background: Base CaP coding agents 
 maestro builds on the design pattern we call Base CaP ,
our name for a representative closed-loop, code-as-policies coding agent for manipulation, exemplified by the Gemini Robotics agent  [ 2 , 4 ] . A Base-CaP system gives a VLM a small inventory of robot APIs and has it write and execute Python in a plan-react-replan loop: decompose the instruction, emit code for a substep, observe the resulting image and stdout , then advance or rewrite. Crucially, it relies on the VLM’s own default abilities: a three-tool inventory in which the VLM itself produces bounding-box detections, 2D points, and top-down grasp poses, alongside basic Cartesian and gripper control  [ 2 , p. 11, Fig. 12] . This places a hard ceiling on the system, which perceives and grasps only as well as a generalist VLM can. We take this configuration as our starting point, the S0 baseline of the scaling study (Sec.  4.4 ) and the “Shared CaP pattern” column of Table  1 . The rest of this section keeps this closed-loop structure but scales it with curated best-quality modules (Sec.  3.2 ) and the robotics-specific orchestration harness they require (Sec.  3.3 ); concurrent code-as-policies efforts that converge on related ideas are discussed in App.  F . 
 3.2 Scaling the tool library: from Base CaP (S0) to maestro (S4) 
 For tabletop manipulation, we experiment with the widely used DROID  [ 29 ] platform visualized in Fig.  1 , a 7-DoF Franka Panda robotic arm equipped with a Robotiq 2F gripper, supported by a wrist-mounted camera and a third-person camera. For this setup,
 maestro ’s tool library is a cumulative progression over the Base-CaP starting point that mirrors the scaling study (Sec.  4.4 ): each stage replaces a capability the Base-CaP VLM handles with its default abilities ( S0 : 2D pointing and bounding boxes, imagined top-down grasps, Cartesian and gripper control) by the curated, best-quality module for that capability. S1 adds a coarse-to-fine perception hierarchy (Grounded-SAM segmentation, FoundationStereo  [ 30 ] metric depth, and ReKep-inspired task-relevant keypoints  [ 31 ] ); S2 adds GraspGen  [ 32 ] 6-DoF grasping and cuRobo  [ 33 ] collision-free motion planning; S3 adds geometry primitives (vector and rotation operations) that supply the metric spatial reasoning current VLMs lack; and S4 treats the π 0.5 \pi_{0.5}   [ 12 ] VLA as a callable policy for short in-distribution skills, run under the monitoring harness of Sec.  3.3 . For the mobile manipulator the same library is extended with embodiment-specific modules (base state estimation, active perception, navigation, a fine-grained “nudge” tool, and a semantic map). Table  1 contrasts the full library with Base CaP, and App.  A.1 (with Sec.  A.3 and Sec.  A.4 ) gives the per-stage and per-module details. 
 3.3 Robotics-specific orchestration: the harness 
 A robotics agent must handle unreliable tool results: perception is noisy, grasps slip, motions are blocked, and learned policies stall. The orchestration problem is thus not just selecting tools but recovering when any tool fails, by re-perceiving, re-planning, or composing a different tool. We use harness for the interface layer that encodes how to use the raw robotics modules correctly, knowledge the VLM cannot reconstruct on its own.
The harness must account for an open physical world the agent does not control, and provide ways to visualize and verify structured outputs such as 6-DoF grasp poses and point clouds before acting on them. Designing this harness is central to maestro , and removing it collapses the without-harness curve of Sec.  4.4 even as tools are added. 
 Concretely, we organize maestro ’s tool interfaces and execution support into five recurring design principles; Table  1 lists concrete additions over our reproduced Base CaP baseline:
 ( a )  encapsulation , bundling an error-prone upstream-to-downstream module chain behind a single call; ( b )  procedural knowledge , injected into the prompt as priorities, guardrails, and worked composition examples; ( c )  closed-loop control , monitoring, success detection, and replanning;
( d )  infrastructure , coordinating shared resources and starting and stopping policy execution (App.  A.2 );
 and ( e )  feedback , rendering otherwise-unreadable tool outputs (e.g., predicted points and 6-DoF poses) back into the VLM’s observation so it can verify them. We describe the harness each tool cluster (S1–S4) requires.

with a sanity-check guardrail ( b ). S3 geometry: purely procedural ( b ), in-context worked examples of composing vectors and rotations. S4 VLA: execute_with_pi05 runs π 0.5 \pi_{0.5} under a parallel ∼ 2 {\sim}2  Hz Qwen-2.5-VL monitor that interrupts on success or replan ( a ,  c ),
with a resource manager coordinating exclusive camera access and starting and stopping policy execution ( d )
; this monitor is precisely what turns a non-terminating policy into a tool the agent can call and reliably stop. App.  A details each. 
 Underlying all of these is the closed-loop control loop ( c ): the plan-react-replan cycle through which every recovery happens. This loop is shared with Base CaP and supports maestro 's per-cluster harness, and we describe it next. 
 Given a task instruction and an image at the start of an episode, maestro first plans , decomposing the task into substeps and generating code for the first; it then reacts , using the instruction, code output, robot state, and post-execution images to judge whether the subgoal was achieved; if so it plans the next substep, and if not it replans , diagnosing the failure and rewriting code for the same substep. This plan – react – replan loop lets maestro continuously adapt to the environment and its own mistakes until the task completes (Alg.  1 , Fig.  8 , App.  A ; interactive replay on our project site ). 
 Fig.  9 (App.  A ) traces one such iteration on the whiteboard-erase task: the react step (Alg.  1 ) localizes a failed eraser grasp and rewrites one line of actor_code to lower the grasp height before the retry succeeds. The loop closes at the code level rather than the retry level: a post-execution image and the robot state let the VLM localize the failure and apply a code edit instead of re-executing. 
 Monitor reliability. A separate human audit of 372 non-idle step-level success/failure judgments across 61 logged trials found 89.8% accuracy, 85.0% precision, and 99.0% recall for success detection. App.  M details the audit. 
 Cross-trial evolution. maestro can also autonomously improve across repeated trials on the same task: after each trial it feeds a structured execution record (generated code, reasoning trace, and a post-execution root-cause analysis) back to the VLM as in-context history, producing targeted corrections that compound without human intervention (formalized in Alg.  2 ; open-cabinet case study in App.  C , results in App.  B ).

 4.1 Real-World Experiment Setup 
 We evaluate maestro in the real world along three axes, manipulation-challenge category, evaluation-setting diversity, and robot embodiment, using Gemini Robotics-ER 1.5  [ 4 ] as its VLM. For our zero-shot results and tool/harness ablations (Secs.  4.2 – 4.4 ), we evaluate maestro without invoking the π 0.5 \pi_{0.5} VLA tool. In App.  K , we evaluate π 0.5 \pi_{0.5} as a callable tool within maestro . 
 Embodiments. We evaluate maestro on two embodiments: a Franka-based DROID tabletop platform  [ 29 ] , which best supports comparison against prior generalist policies (tabletop being the most widely studied domain), and a Unitree Go2-W wheeled quadruped with a top-mounted AgileX PiPER arm for mobile manipulation. Full hardware and camera configurations are in App.  D . 
 Tasks. We identify the key challenge axes facing today’s generalist robot policies and evaluate maestro on eight tabletop and four mobile manipulation tasks. The eight tabletop tasks span pick-place, deformable object, articulated object, spatial reasoning, tool use, object affordance, long-horizon semantic, and memory challenges (Fig.  3 ); the four mobile tasks span long-horizon manipulation, long-horizon loco-manipulation, active exploration, and object-affordance reasoning (Fig.  5 ). Each figure visualizes every task with its instruction. 
 Evaluation Protocol. We adopt the STAR-Gen taxonomy of generalization  [ 34 ] . For each task, we evaluate five settings held fixed across methods: one initial setting and four settings generated using STAR-Gen, with perturbations to task-relevant object appearance, object poses, action verbs, and object identity. These are distinct settings rather than repeated runs of an identical scene. The tabletop comparison comprises eight tasks and four methods, for 40 40 scored trials per method and 160 160 trials in total. Following π 0 \pi_{0}   [ 1 ] , we score task progress per trial for quantitative results (App.  E ). 
 Human reviewers assigned all task-progress and task-completion scores independently of the agent’s monitor.

 Baselines. 
We benchmark maestro against open-source generalist robot policies from both the Code-as-Policies (CaP) and VLA paradigms. For CaP,

Our baseline implementation follows the system-prompt structure, three-tool inventory (top-down grasp prediction, 2D bounding-box detection, 2D pointing, all performed by the VLM itself rather than via external robotics models), and intra-episode replan loop documented in  [ 2 , Fig. 12, App. B.3.2] . This corresponds to the “Shared CaP pattern” column of Table  1 (App.  A ). 
 We implement this using Gemini Robotics-ER 1.5
  [ 4 ] and denote it as the Gemini Robotics Agent .
For VLAs, we compare against π 0 \pi_{0} 
  [ 1 ] and π 0.5 \pi_{0.5}   [ 12 ] . Specifically, we use the π 0 \pi_{0} -FAST-DROID checkpoint for π 0 \pi_{0} ( π 0 \pi_{0} -FAST fine-tuned on the DROID dataset) and the π 0.5 \pi_{0.5} -DROID checkpoint for π 0.5 \pi_{0.5} , which is similarly fine-tuned. 
 Results. Fig.  4 summarizes the tabletop results, with detailed numbers in App.  G . maestro has the highest mean task progress on six of eight tasks in the selected five-trial comparison. π 0.5 \pi_{0.5} has the highest mean on fold towel and hang mug on mug holder. VLA baselines struggle on several perturbed settings and lack an explicit memory mechanism. Their mean progress is low on open cabinet; on rotate cube, the selected trials yield means of 23.0 23.0 for π 0 \pi_{0} and 30.0 30.0 for π 0.5 \pi_{0.5} , compared with 88.0 88.0 for maestro . The Gemini Robotics Agent, our CaP baseline, plans well but struggles to turn high-level plans into low-level actions: its agentic loop is built around Gemini’s own perception  [ 2 , p. 11] , so it is limited to whatever bounding boxes, points, and top-down grasps the VLM produces on its own, and cannot, for instance, localize a cabinet handle without active perception or grasp and orient an eraser or towel corners without external segmentation, depth, and grasp modules. 
 maestro bridges this gap less through the tool modules than through the orchestration harness around them (Sec.  3.3 ): it hides error-prone chains like point-cloud reconstruction and grasp prediction behind single calls (encapsulation), injects procedural guidance on module choice and exact geometry for reorientation, and renders tool outputs back for the VLM to verify points and 6-DoF poses. When a step fails, its closed-loop plan-react-replan cycle re-perceives and recomposes tools, e.g., recovering from a failed top-down grasp of a shelved tennis ball via active perception and the grasp model for a safer, reachable pose. This lets maestro surpass prior CaP systems in dexterity and task coverage on tasks typically considered better suited to VLA-style approaches, though hang mug on mug holder still exceeds its affordance and orientation reasoning. Rollout videos for all eight tabletop tasks are on our project site .

 4.4 How important is each component of maestro ? 
 Table  1 (App.  A ) lists the tools and harness components that maestro adds over Base CaP. We examine their contributions by expanding the tool library from Base CaP (S0) through advanced perception (S1), grasping and control (S2), and geometry and spatial reasoning (S3). At each stage we compare four conditions: Full harness (I+E) , Interface only (I) , Execution only (E) , and No harness . Following the five harness principles defined in Sec. 3.3, Interface retains encapsulation and procedural knowledge, while Execution retains closed-loop control, infrastructure, and feedback. We group the latter three because they work together during and after execution. We report per-task progress for opening a cabinet, rotating a cube so a target face points up, and grasping a knife by its handle to cut a banana. Aggregate values are unweighted means of these three task means.

 Results. Fig.  7 shows that the full harness has the highest or tied mean in all nine S1–S3 task-stage comparisons. Its three-task average rises from 32.3% at S0 to 44.0% at S1, 57.7% at S2, and 76.9% at S3, although individual tasks need not improve at every stage. At S3, Interface only reaches 59.3%, Execution only 34.0%, and No harness 33.0%. The partial-harness variants generally fall between full and no harness, but Execution only is lower than No harness for open cabinet at S3 (6% versus 11%). These results support the value of the full harness in this setting and show that adding tools alone does not reliably improve progress. 
 Complementary analyses corroborate this: per-module leave-one-out ablations (App.  H ) provide additional module-level comparisons, and a tool-call-level analysis (App.  I ) shows maestro composes task-specific rather than fixed workflows, with 47 of 63 initially failed subtask instances later receiving a logged success judgment (74.6%). This conditional, log-derived recovery statistic is distinct from human-scored trial completion. The scaling study evaluates S0–S3; the contribution of the S4 VLA tool is evaluated separately in App.  K . 
 4.5 Beyond single-trial execution 
 Beyond single-trial execution, we examine three capabilities in preliminary case studies. maestro can refine its generated policies across trials: on one selected open-cabinet trajectory, three rounds of code refinement improve progress from 35 % 35\% to full completion (App.  C ). It can combine task-level planning with faster VLA execution: on table cleanup, invoking π 0.5 \pi_{0.5} as a tool raises mean progress from 89 % 89\% to 94 % 94\% and reduces mean completion time by 2.3 × 2.3\times (App.  K ). It can also be used for automatic data generation: starting from 10 maestro execution rollouts, Tether  [ 35 ] generates a larger dataset across new scene configurations. On two tasks, this pipeline performs comparably to Tether initialized with human-teleoperated demonstrations (App.  L ). 
 5 Limitations and Future Work 
 maestro ’s closed-loop harness catches and recovers from individual tool failures rather than assuming every module always succeeds, which is much of why it outperforms a naive composition of the same tools. Recovery has limits, however: when a module is systematically wrong in a way maestro cannot observe or route around, the error propagates to the task. These residual failures concentrate in perception and low-level control, and more delicate control will require richer low-level behaviors than the current toolset supports.
 Runtime remains a limitation (App.  J ): querying a VLM during planning and replanning makes maestro slower than end-to-end VLAs such as π 0.5 \pi_{0.5} . Recent direct-control evaluations of GPT-6 Astra show that inference can take much longer than the robot motion it specifies  [ 6 ] . Delegating low-level control to tools avoids generating every action with the VLM, but repeated planning and verification still incur latency and token charges. Future work will explore how to reduce VLM calls while preserving timely failure detection, and how to distill frequently repeated behaviors into faster policies. 
 6 Conclusion 
 We present maestro , a VLM-driven coding agent for tabletop and mobile manipulation, equipped with a curated tool library and the orchestration infrastructure to compose and adapt these tools. Without collecting new teleoperation data, it outperforms the evaluated VLAs and Base CaP system in our tabletop comparison. Ablations highlight the importance of the harness: adding tools alone does not reliably improve performance. Its modular interfaces allow improved tools and VLMs to be incorporated as they become available, offering a complementary route to scaling robot data.

 A.1 Tool library by scaling stage (S0–S4) 
 This subsection gives the staged description of maestro ’s tabletop tool library summarized in Sec.  3.2 , presented as a cumulative progression over the Base-CaP starting point that mirrors the scaling study of Sec.  4.4 : each stage replaces a capability the Base-CaP VLM handles with its default abilities by the curated, best-quality module for that capability. Table  1 (a) lists the same library compactly, and Sec.  A.3 and Sec.  A.4 give the full per-module mechanics. 
 S0 (Base CaP): the VLM’s default abilities. The starting point exposes only what the VLM can do by default (Sec.  3.1 ): 2D pointing and bounding boxes for localization, VLM-imagined top-down grasps, and basic Cartesian and gripper control. Each cluster below replaces one of these defaults with the best-quality module available for that capability. 
 S1 (+advanced perception). We replace the VLM’s default perception with a coarse-to-fine hierarchy of specialized vision modules that lets the agent trade speed against precision: raw RGB and proprioception (fastest, coarsest); Grounded-SAM segmentation-mask centroids and 2D pointing (medium); FoundationStereo  [ 30 ] metric depth, which supplies the reliable 3D positions and dense object point clouds that the VLM’s monocular guesses cannot; and VLM-selected task-relevant keypoints (ReKep-inspired  [ 31 ] ) for precise but slower localization of features a VLM struggles to point at directly. Two harness capabilities, active perception and image-editing feedback , make this hierarchy usable in practice; we detail them with the rest of the perception harness in Sec.  3.3 . None of these abilities exist in Base CaP, which perceives only as well as the generalist VLM itself, with no metric depth and no point clouds. 
 S2 (+grasping and control). Base CaP can only execute the top-down grasps the VLM imagines and moves the arm by direct Cartesian servoing with no notion of obstacles; we replace both. For grasping, GraspGen  [ 32 ] is a learned grasp model that predicts ranked 6-DoF grasps on an object’s point cloud, expressing the side, angled, and functional-part grasps a top-down pose cannot. Because grasp quality hinges on a clean point cloud, the grasp pipeline first drives a planned multi-view scan of the wrist camera and fuses the views into a single object point cloud before prediction. For control, we add cuRobo  [ 33 ] point-cloud-based collision-free motion planning, letting maestro reach those grasps and move through cluttered scenes while avoiding unintended contact, which is essential whenever the arm must make and break contact with objects or operate around obstacles. Both capabilities are entirely absent at S0–S1, where the agent has neither a 6-DoF grasp source nor any collision awareness. 
 S3 (+geometry and spatial reasoning). In our initial experiments, the agent struggled with metric spatial reasoning even with improved perception. We therefore provide explicit tools for computing distances, vectors, and rotations from perception outputs. These tools are not included in the Base CaP baseline. 
 S4 (+VLA). Finally, maestro treats a learned visuomotor policy, π 0.5 \pi_{0.5}   [ 12 ] , as a callable tool for fast, reliable execution of short skills such as pick-and-place. A raw VLA has no self-termination signal, so exposing it as a usable tool depends on the monitoring harness of Sec.  3.3 ; the agent selects the VLA only when it fits the subtask (App.  B ) and falls back on the procedural modules above otherwise. 
 Mobile manipulation. For the mobile embodiment, the same library is extended with embodiment-specific modules: mobile-base state estimation, active-perception tools (look left / right / ground, view the carry-on basket, log object locations), navigation, a fine-grained “nudge” tool for local base adjustment, and a semantic map that caches observed object locations to support persistent reasoning over long-horizon tasks. 
 A.2 Per-stage harness details 
 This subsection gives the full mechanics of the per-cluster harness summarized in Sec.  3.3 , one paragraph per scaling stage; Table  1 (b) lists the same infrastructure compactly, and the tags ( a )–( e ) refer to the five harness design principles of Sec.  3.3 . 
 S1 perception harness. The perception harness adds: priority guidance on which localizer to try first and when to escalate from pointing to segmentation to keypoints, plus a “detect all objects once and cache” rule that avoids repeating an ∼ 30 {\sim}30  s scan ( b ,  d ); active perception that lets the agent reposition the wrist camera, zooming in or looking around, so the downstream segmentation, depth, and keypoint tools receive informative observations, since off-the-shelf vision models are only as good as the views they are given ( d ); image-editing feedback that draws predicted points and 6-DoF poses back onto the observation image, so the VLM can visually confirm a result it cannot read as raw numbers ( e ); and an encapsulated keypoint tool that hides a multi-step pipeline behind one call: best-view selection, segmentation, candidate-point sampling, image rendering, depth projection, and a second VLM that picks the matching point ( a ). 
 S2 grasp and control harness. 
For grasping, encapsulation ( a ) packages a multi-step tool chain behind a single call.
 A single get_grasp_pose call internally runs active perception (a planned spherical look-around of the wrist camera with multi-view fusion into a clean object point cloud), then segmentation, depth, and GraspGen, returning a ranked 6-DoF grasp; a companion plan_grasp fuses that grasp with control, applying a gripper-flange calibration offset and collision-free planning before executing ( a , plus calibration knowledge the VLM should not manage). Prompt-level guidance adds a grasp sanity-check guardrail and side-vs-top-down strategy ( b ). Because these modules are heavy, the harness runs them on a GPU server, handling file sync and client–server communication, and a scene-scan cache persists multi-view captures for reuse ( d ). The agent simply asks for a grasp. 
 S3 geometry harness. The geometry primitives are already atomic, so their harness is purely procedural ( b ): in-context worked examples of composing vectors and rotations (e.g. building an axis from two keypoints and rotating about it) and guidance on when to use them for orientation, so the agent reaches for exact geometry instead of guessing poses. 
 S4 VLA harness. π 0.5 \pi_{0.5} runs fast but has no signal for when it has finished. maestro wraps it in execute_with_pi05 ,
which runs the policy alongside a separate Qwen-2.5-VL monitor
 that checks task-relevant completion conditions on the live image at ∼ 2 {\sim}2  Hz and interrupts the policy on success or when a replan is needed ( a ,  c ).
A resource manager coordinates exclusive camera access and handles starting and stopping policy execution, allowing the VLA to run alongside the main coding agent ( d ).
 This monitor is precisely what turns a non-terminating policy into a tool the agent can call and reliably stop. 
 Curating for quality, not for external models per se. The best-quality modules maestro adopts are usually specialized, externally-developed systems, but that is a consequence of curating for quality rather than a goal in itself, since the generalist VLM is rarely the best tool for a precise robotics subtask. 
 Mobile-manipulation replanning. In mobile manipulation settings, before performing failure analysis and rewriting code, maestro is also prompted to actively look around and perceive the environment to build a more complete understanding of its surroundings before it replans.

 A.3 Tabletop Manipulation Modules 
 We equip our tabletop manipulation agent with a suite of tools spanning perception, reasoning, control, pre-trained visuomotor policies, and image editing. The tools are provided in bolded text below. 
 Perception. For perception tools, we adopt a “coarse-to-fine” approach. At the fastest and simplest level, the agent can access raw sensory inputs (RGB images and robot proprioception). Because raw depth is often noisy, we use FoundationStereo  [ 30 ] to estimate more reliable depth maps from RGB. For object center point , given a language description, we employ Grounded-SAM to produce a mask and its center point, while a Gemini-based pointing tool returns single 2D points corresponding to language queries. For tasks requiring higher precision—such as grasping towel corners—we provide a salient task-relevant points tool inspired by ReKep  [ 31 ] : after generating a segmentation mask, we overlay a uniform point grid and ask GPT-o3 to select the most relevant points. This tool hierarchy balances granularity and runtime: raw images are coarse but fast, while salient points are slower but more precise. maestro autonomously reasons about which tools to use and how to use them for each task, achieving a balance between execution speed and task performance. As an alternative, we also provide language-based pointing using Gemini Robotics-ER 1.5  [ 4 ] . 
 Reasoning. In our initial experiments, maestro struggled with task-relevant spatial reasoning even with advanced perception tools. We therefore provide tools for explicit spatial calculations: measuring distances , constructing vectors using points , computing relative rotations between vectors , and rotating a vector by specified angles . 
 Control. For low-level manipulation, we provide Cartesian end-effector control tools: move gripper to , open gripper , and close gripper . We use cuRobo  [ 33 ] for point-cloud-based motion planning with collision checks. At the grasping stage, collision checking is disabled only for the gripper links identified by the robot and gripper URDFs; checks remain active for the rest of the robot. This contact exception does not model the grasped object as part of the robot, so collisions involving held objects remain a limitation (App.  J ). 
 Learned Visuomotor Policies. We equip maestro with two types of learned visuomotor policies: a grasp model and a VLA . For grasping, we provide GraspGen  [ 32 ] , while for general-purpose low-level visuomotor control we provide the state-of-the-art π 0.5 \pi_{0.5} model  [ 12 ] . A key challenge when integrating end-to-end VLAs as tools is determining when to interrupt their execution, since they continue running inference until externally stopped. We use a separate completion monitor running at 2 Hz, hosting Qwen-2.5-VL-72B-Instruct locally to check task completion with a yes/no question and interrupt execution when completion is detected. 
 Image Editing. Prior work  [ 37 , 38 ] shows that adding visual marks can improve the grounding and reasoning abilities of VLMs. Thus, we provide maestro with image-editing tools that can draw points and overlay 6D poses on images, enabling clearer spatial references and richer visual reasoning during manipulation. Concretely, maestro draws the 2D points returned by its pointing tools back onto the observation so the VLM can confirm a target selection before acting (e.g. verifying which object or contact point was chosen in spatial-reasoning and pick-place tasks), and overlays a candidate 6D grasp pose so the agent can check the gripper’s approach direction against object affordances (e.g. confirming a knife is grasped by the handle, or a mug at an orientation that permits hanging). The edited image is fed back into the next replanning step, closing the loop on these checks. 
 A.4 Additional Modules for Mobile Manipulation 
 To extend beyond tabletop tasks, we equip maestro with additional tools that enable mobile manipulation. 
 Perception. For a mobile manipulator, obtaining the full robot 6D state requires more than raw proprioception. We therefore employ Faster-LIO  [ 39 ] , a lightweight LiDAR–Inertial Odometry method, to provide robust state estimation of the mobile base even under visually challenging conditions. This enhanced perception ensures reliable navigation and spatial reasoning across larger workspaces. In addition, mobile manipulation benefits from active perception to build a more complete understanding of the surroundings and gather task-relevant information on demand. To this end, we provide maestro with active perception tools— look left , look right , look to the ground , and view carry-on basket , remember object location —which allow it to scan the environment, adjust its viewpoint, and access the basket contents as needed. 
 Locomotion. We supply two tools: (1) the nudge tool, which applies small velocity adjustments for precise positioning near a target location, and (2) the navigation tool, which leverages Nav2 [ 40 ] to move the robot safely to a target pose on the map. This dual interface allows maestro to fluidly switch between global navigation and fine-grained local control. 
 Manipulation. To support transport tasks, we provide a dedicated put in basket tool that enables the robot to efficiently carry multiple objects during long-horizon mobile manipulation. For unloading, maestro leverages the view carry-on basket perception tool to inspect the basket’s contents and then automatically generates the code needed to move objects out of the basket.

 We present a case study of maestro ’s evolution mechanism (the outer loop of Algorithm  2 , App.  A ) on the open-cabinet task. The trajectory starts from the least successful initial run ( 35 % 35\% progress). Fig.  10 shows the policy abstraction, strategy change, and outcome at each refinement stage. 
 Trial 0 (Initial, 35%). maestro identified the handle but used a top-down grasp and a fixed straight-line pull ([0.0, 0.15, 0.0]) that ignored the hinge kinematics, leaving the door closed. Reflection correctly attributed the failure to the linear motion primitive. 
 Trial 1 (Evolve #1, 70%). maestro restructured the motion strategy: it added perception of the top-right and bottom-right door corners to estimate the hinge axis, then replaced the straight pull with a hinge-arc trajectory (75°, 10 waypoints). The door began to open, but the handle slipped mid-arc because the grasp could not sustain the rotational forces. 
 Trial 2 (Evolve #2, 85%). To counter the slip, maestro added a post-grasp stabilization step (a 2 cm upward lift to tighten the grip), widened the arc to 80°, and refined the rotation to incremental orientation updates in the 2D plane. The door reached about 45° before the handle slipped again. 
 Trial 3 (Evolve #3, 100%). maestro replaced the lift with a combined retract-and-lift (2 cm + 2 cm) that pre-tensions the grasp, widened the arc to 85°, increased waypoints from 10 to 15 (smoother, lower-jerk trajectory), and added incremental yaw tracking so the gripper follows the arc. These changes eliminated grasp slip and the door opened to about 80°. 
 Across four autonomous trials, maestro progressed from a linear pull to a kinematically grounded arc policy with robust grasp stabilization, showing that video-grounded self-reflection enables improvements in generated robot programs across trials without human guidance.

 Appendix F Extended discussion on prior work 
 A wide range of prior work has explored the use of large models — Vision-Language Models (VLMs) and Large Language Models (LLMs) — to support specific components of robotic systems. In the common paradigm, these models are embedded into manually designed, typically rigid, modular pipelines, where large models take on one or several well-defined roles while the remaining pipeline is built through “good old-fashioned engineering” by humans. These roles span reward and environment design  [ 41 , 42 , 43 , 44 , 45 ] , constraint-function design  [ 46 , 47 , 31 , 48 ] , high-level planning  [ 49 , 18 ] , self-reflection  [ 50 ] , visual question answering  [ 51 , 38 , 52 , 53 ] , in-context learning  [ 54 , 55 ] , and task-progress evaluation  [ 56 , 57 , 58 ] . 
 While effective within their intended scope, these approaches remain constrained by their rigid workflows. Because large models automate only a small portion of the pipeline, substantial manual effort is still required to design the rest. This rigidity also limits scalability: systems tuned and fixed for specific settings struggle to generalize to diverse, in-the-wild scenarios. As a result, these methods fall short of the requirements for scalable, general-purpose robotic manipulation. 
 Rather than reworking the agentic architecture, maestro builds on the closed-loop VLM coding-agent pattern of recent CaP-based manipulation systems such as Gemini Robotics  [ 2 , 4 , 36 ] . Our contribution is the design of the harness around that shared pattern: rather than relying on the VLM for perception, maestro composes curated external robotics models as callable tools (Table  1 ), letting the system inherit ongoing advances in those subfields without retraining. The result is a system that can autonomously decide how , when , and which modules to employ. In doing so, we show that, alongside the dominant data-scaling route to generalist manipulation, investing in this kind of agentic system is a complementary axis that already yields VLA-level performance without new teleoperation data. 
 Hierarchical and reasoning-augmented VLAs. Several VLA variants augment the action-generation backbone with language or reasoning while still selecting actions through a fine-tuned VLA: Hi Robot  [ 10 ] decomposes user instructions into natural-language sub-commands that a learned VLA executes, and ECoT-Lite  [ 9 ] distills efficient embodied chain-of-thought reasoning directly into the VLA. 
 Concurrent code-as-policies efforts. Several recent efforts explore approaches related to maestro . CaP-X  [ 27 ] from NVIDIA proposes a benchmark and framework for code-as-policies coding agents, validated on a Franka arm in simulation and on real hardware, and shares our focus on multi-turn interaction, structured feedback, and skill synthesis. GaP  [ 28 ] uses a multi-agent coding harness to construct graph policies from modular robot skills and refine them through simulation rehearsal for variational automation. Gemini Robotics 1.5  [ 4 ] introduces an ER/VLA stack with generic third-party tool-calling, and Gemini Robotics-ER 1.6  [ 36 ] adds Python-based image manipulation for ambiguity resolution. We view this convergence as encouraging evidence that the route is worth pursuing; maestro ’s complementary scope is its curated, robotics-specific module library and the orchestration harness built around composing those models in a real-world generalist system across diverse tasks and embodiments. 
 Appendix G Detailed Tabletop Manipulation Results 
 This section provides additional details on the tabletop manipulation results summarized in Fig.  4 of the main text. Table  2 reports the mean and standard error of task progress scores across all five evaluation trials for each task and method. 
 Qualitative analysis. VLM-based agents excel at high-level semantic reasoning and planning. However, our CaP baseline, the Gemini Robotics Agent, still struggles to turn these high-level plans into effective low-level actions. Its agentic loop is designed around Gemini’s own perception capabilities  [ 2 , p. 11] , so on harder tasks the agent is constrained by whatever bounding boxes, points, and top-down grasps the VLM can produce on its own. In open cabinet, this means the agent cannot localize the handle without an active-perception scan, and its top-down grasping strategy no longer applies. Similar limitations show up in fold towel and erase whiteboard, where the agent can plan but cannot localize towel corners or correctly grasp and orient the eraser without external segmentation, depth, and grasp-prediction modules in the loop. 
 maestro bridges this gap by coupling VLM-level semantic reasoning with a broad suite of specialized tool modules. It leverages grasp models for reliable pick-and-place, active perception modules for accurate point-cloud reconstruction of cabinet handles, task-relevant keypoints for towel corner localization, and geometric reasoning to rotate objects to precise orientations (e.g., turning a cube to place a target color face upward). When errors occur, maestro ’s “react and replan” mechanism analyzes execution history and images, then revises its code and module orchestration. For example, to pick up the tennis ball on the shelf, it first attempts a top-down grasp but, after detecting rolling and collision risks, switches to active perception to refine the point cloud and leverages the grasp model tool to generate a safer, reachable grasp pose. Nevertheless, the “hang mug on mug holder” task reveals maestro ’s current limitations: when complex chain-of-thought reasoning about object affordances and spatial orientation is required, it can still struggle. In this case, it fails to correctly align the mug handle’s hole with the branch orientation of the holder.

 Appendix J Detailed Failure-Mode Analysis 
 maestro ’s failures concentrate in a few module classes rather than in high-level planning: imprecise pointing and segmentation under difficult lighting, motion-planning infeasibility and over-conservative collision checking, geometrically valid but task-inappropriate grasps, and, on the mobile platform, occasional default navigational fallbacks. This appendix enumerates the full per-embodiment failure modes, with concrete trial examples, below. 
 The Agent Dashboard on our project site provides interactive trial replays that show how some of these failure modes surface in maestro ’s plan-react-replan loop, including a recovered case where maestro detects an incomplete erase and replans autonomously. 
 Mobile platform 
 1. 
 False Negatives. In collect all toys , YOLO never detected the strawberry plushy, so the system reported the task 100% complete. 
 2. 
 Color Confusion. In collect all toys , the system misidentified a red plushy as pink. 
 3. 
 Lighting and Motion Sensitivity. In press button , motion blur combined with sunlight produced a “bad image” for the pointing module, sending the robot to the wrong position when approaching the door button. 
 4. 
 Pointing Precision. In throw garbage , the VLM did not point to a reasonable location on the garbage can, so the dropped object landed half-on the rim. 
 5. 
 Global-to-Local Viewpoint Selection. The agent struggles to switch from macro-navigation (using the global 3D semantic map) to micro-manipulation. In throw garbage , the initial observation correctly noted that the garbage can was on the floor, but on arrival the VLM defaulted to a “FRONT” camera pose and never pitched “DOWN,” so the short can was invisible at execution time. 
 6. 
 Invalid Pose Generation. The kinematic solver occasionally fails to produce a feasible end-effector orientation. In throw garbage , no valid release pose was found at the end of the trajectory, preventing the robot from dropping the green plush ball into the can. 
 7. 
 Default Navigational Fallback. When given new action verbs, the VLM falls back on default navigational behaviors instead of adapting to the verb’s meaning. In Task 3 Trial 5, the instruction was modified to “hand it to the nearest person”; rather than visually searching for a human, the VLM returned to map origin [ 0 , 0 , 0 ] [0,0,0] . 
 Tabletop platform 
 1. 
 Incomplete Collision Modeling of Grasped Objects. cuRobo  [ 33 ] models the arm but not the grasped object, so the held object can still collide with surroundings in clutter even though the arm itself stays clear. 
 2. 
 Pointing Inaccuracy. Both VLM-based pointing (Gemini Robotics-ER 1.5) and segmentation-based pointing (Grounded-SAM2) lack the precision to localize fine-grained regions reliably, especially when multiple points are needed. VLM-based pointing also confuses certain color pairs (red/yellow, blue/yellow); segmentation-based pointing degrades under bright lighting. 
 When a perception error is visible in the returned observations, maestro can acquire a new view, repeat perception, and replan. This does not cover undetected errors, which can propagate into later actions. The tool interface allows improved perception modules to replace existing ones without retraining the orchestration policy. 
 3. 
 Motion Planning Infeasibility. VLM-selected end-effector poses are sometimes kinematically unreachable or unsolvable by cuRobo. cuRobo’s collision checker is also over-conservative, flagging intended contacts (e.g., cutting, insertion) and blocking the interaction. 
 4. 
 Insufficient Semantic Grasp Selection. GraspGen  [ 32 ] returns geometrically valid grasps but does not reason about task affordances, so the robot may grasp a knife by the blade or a mug by an orientation that prevents the planned hang. 
 5. 
 Limited Spatial Reasoning for Complex Affordances. Tasks requiring precise relative-orientation reasoning, such as hanging a mug on a holder, remain hard: the VLM fails to align the handle opening with the holder branch and to leave clearance along the insertion direction, often knocking the holder over. The available geometry and vector tools are not consistently leveraged for these multi-step alignments. 
 6. 
 VLM Inference Latency. Each plan-react-replan iteration calls the VLM, making maestro considerably slower than end-to-end VLA policies such as π 0.5 \pi_{0.5} . Reducing VLM inference latency and overall compute cost remains an important direction for future work.

 Appendix L Automatic Data Generation: Tether Case Study 
 This section provides additional background on the Tether framework  [ 35 ] used in our autonomous data collection experiments (App.  B ). 
 Tether is a framework for automatic robot data generation: starting from as few as 10 recorded execution rollouts, it adapts their trajectories to new scene configurations to generate a larger, diverse dataset. The key insight is correspondence-driven trajectory warping : given a recorded rollout in one scene configuration, Tether extracts a small set of task-critical waypoints from that rollout (end-effector poses at frames where the gripper open/close state toggles) and uses DINOv2/Stable-Diffusion-based semantic correspondences to locate the matching waypoints in a new scene (e.g., with different object poses or instances). The 2D matches are backprojected to 3D via stereo, yielding per-waypoint displacements that are linearly interpolated along the recorded trajectory to warp the full end-effector path (timing rescaled to preserve speed), producing a new trajectory that accomplishes the same task under different conditions. We refer the reader to [ 35 ] for full details on the correspondence computation and warping procedure. 
 In our experiments, maestro supplies the initial execution rollouts in place of human teleoperation. Tether then uses these recordings to generate data across new scene configurations. Only environment resets are manual: between rollouts, a human resets the workspace with deliberately varied object placements (and, where applicable, object instances), and Tether adapts a recorded trajectory to each new configuration, so the dataset grows by one trajectory per reset. 
 We detail below the autonomous data-collection experiment summarized in App.  B .
